# Build Checklist

Build mode: learn

Commits: many small commits per slice — one per new feature, backend and Android separately (learner request). A slice's `Commit:` line names its last commit.

## Slices

  PRD ref: `prd.md > The Core Journey` (steps 1–4, 12–13), `prd.md > Account and Session`, `prd.md > Screens and Layout`, `prd.md > Look and Feel`

## Revisions

- Spec aligned to real email + password accounts (BCrypt, session token, Profile with Log out) — `spec.md` described a name-only mock login that contradicted the approved `scope.md` and `prd.md`; the learner confirmed real accounts at the start of `5-build`.
- Spring Boot 4.1.1 instead of 3.x — start.spring.io no longer offers 3.x (its open-source support has ended); the learner chose 4.1.1.
- City autocomplete on Create account (Open-Meteo Geocoding via `GET /api/cities`), city required and stored with country + coordinates — learner request during slice 1; small added cost (one public endpoint, no key).
- The learner's screen design (`Mixyn App Screens.pdf`) became the Look and Feel source: mocha primary color, Instrument Serif + Inter, reusable components and a single spacing scale; password minimum raised to 8 to match it; Apple/Google sign-in, Forgot password and Terms removed; Collections shown as "coming soon".
- Android `targetSdk` 36 instead of 37 — the build found that Android 17 silently drops connections from apps targeting 37 to the local network (the backend at 10.0.2.2) unless they request a new runtime permission.
- "Account created" is a separate screen instead of a dialog — learner request, from the updated design (page 4a).
- rembg runs from our own small image (`rembg/Dockerfile`) instead of `danielgatis/rembg` — that image has no arm64 build for Apple Silicon. The image pins the `u2net` model (baked in, so no first-run download) because rembg's newer default model is 1 GB, was killed for memory in a 4 GB Docker, and is non-commercial; requests must send `model=u2net`.
- rembg is published on host port 7010, not 7000 — macOS already uses 7000 (AirPlay Receiver).
- HEIC photos are supported on the server via `pillow-heif` in the rembg image — verified with a test HEIC before slice 2, so iPhone photos (and a future iOS app) work without client-side conversion.
- Gemini calls go through an ordered list of fallback models with an 8 s timeout each — the build found the free tier unreliable for a single model (503 "high demand", 12-27 s answers, and a 429 daily quota on `gemini-3.5-flash` after ~30 test calls). Lite models go first because their free quota is larger.
- Uploads are limited to one photo at a time with an explicit message, and photos that aren't a single clothing item (person, several items, not clothing) are rejected by the same Gemini call — learner requests during slice 2; no extra AI requests.
- Rotation is a user action on the item card (slice 3), not an AI task — the learner asked for AI auto-rotation, saw it miss an upside-down pair of shoes in testing, and chose a manual option instead.
- The stored cutout is cropped to the item and scaled to max 1024 px, and the phone shrinks photos to 1600 px before upload — keeps the grid tidy and uploads fast.
- Items get a **type** from a fixed list kept on the backend (about 30 types, each mapped to Top / Bottom / Shoes / Outerwear); the AI must choose from the list and the user picks with autocomplete — learner request after slice 2. A store's category API (Stradivarius, Bershka) was considered and dropped: no public API exists, so the list is our own. Built in slice 3 with the item card.
- The item card follows the updated design (pages 9–11): the single rotate button became an "Edit photo" sheet with size, rotate left/right, mirror, Reset and Done; the card also got the next-item arrow and the bottom bar — learner's updated design during slice 3. The backend's rotate endpoint became `POST /api/items/{id}/photo`.
- Items can have up to three colors from a fixed 18-color palette kept on the backend (the AI and the user both choose from it) instead of one free-text color — learner request; the AI had described a striped sweater as just "Grey".
- The next-item arrow beside the photo was removed from the item card — the learner tried it and saw no need for it.
- An item can have several seasons instead of one, and the "Edit photo" sheet got a light dim so its edge and rounded corners are visible — learner feedback while checking slice 3.
- On the canvas the hint is typed in an "Ask AI" sheet instead of a field under the canvas, and outerwear is changed with a small "Add a layer" button rather than by swiping — follows the learner's canvas design (page 14), where the top and the outer layer share the same area.
- The stylist understands occasions and full descriptions, and remembers the session's earlier requests so follow-ups change only what was asked — learner requests while checking slice 4. Memory lives on the phone and is sent with each request; the backend stays stateless.
- Weather came back into the PoC in a minimal form (a chip on the canvas and one line for the stylist, via Open-Meteo using the saved coordinates) — learner decision during slice 4; `scope.md` had it under Later / Explicitly Cut. The cold-weather layering step from the design stays out.
- Canvas layout follows the design more closely after the learner's review: outerwear is half a jacket over the left side of the top, shoes are smaller and lower, the header has the weather chip and Next, and the bottom panel has Add bag / Accessory ("Coming soon") beside Ask AI.
- The "Add a layer" button was removed from the canvas — it isn't in the learner's design (page 14). Outerwear now appears only when the stylist adds it; a manual way to choose a layer is an open question for the learner.
- The canvas got the learner's own layer design, replacing page 14's bottom panel: three equal tiles — **Outerwear**, **Bag**, **Accessories** — and Ask AI as a round button at the side. Tapping a tile puts that layer on and locks the rest of the outfit until **Done** (or **Remove**); Accessories first asks which kinds to wear. Outerwear hangs from the top's shoulder line as its left half; a coat or trench reaches down over the bottom. Bags and accessories became real item categories (`BAG`, `ACCESSORY`) with their own types, and the stylist may add them. The weather chip and Next offer a beanie / scarf / gloves in the cold and a cap / hat / headscarf in the heat when the closet has them and the outfit doesn't — a suggestion, never added silently. This brings bags, accessories and weather triggers in from `scope.md > Later`.
- Follow-ups from the learner's review of the layers: a long puffer is its own type (**Puffer coat**) and hangs over the whole outfit like a coat; a layer the closet has nothing for opens a dialog with **Add to wardrobe** / **Skip** instead of a toast; the weather tip also appears when it is merely cool, offers a jacket next to the beanie, scarf and gloves, and shows each piece as a card the user can untick (as on design page 15).
- What counts as "one item" was widened after the learner tried real shop photos: a piece worn or held by a person is accepted when it is the clear subject (a headscarf on a model) — the background is removed as usual and the cutout is cut down to the box the AI draws around the piece, so the face under a scarf stays but the rest of the body goes; a shirt with its tie or a brooch is one item, a single glove is still Gloves; a whole outfit, or pieces that belong apart (shirt + trousers, shirt + jacket), are still turned away. **Zip-up** is a new type and always outerwear; a **Cardigan** is a top that can also be worn as outerwear — the canvas offers it in both places but never as both at once.
- A fourth layer tile, **Under layer**, puts a second top behind the top (a white T-shirt under a sweater) — learner request. Only thin tops can go under: T-shirt, shirt, and two new types, **Long sleeve** and **Tank top**. The under piece must show at the neck and below the hem whatever the two lengths are, so it is drawn in two halves behind the top (collar half placed by the neckline, hem half by the hem, the seam hidden behind the top) and only down a middle strip, so T-shirt sleeves don't stick out. With an under layer on, the top is drawn over the bottom instead of tucked in, so the hem hangs over the trousers. The stylist can add one too (a thin top marked `underLayer` by the backend, never the top itself). **Add to wardrobe** from a missing-piece dialog now brings the user straight back to the outfit once the piece is added, with the new piece put on.
- A piece is worn in one place at a time — learner feedback: a piece that is on as the under layer or the outerwear is no longer offered as the top (before, choosing it as the top silently took the layer off). **Open-front pieces** (an open cardigan, an unzipped zip-up): the tagging call now also answers `front: OPEN|CLOSED` and where the opening is, stored with the item. On the canvas, while something is worn under such a top, the inside of its back is left out and the piece underneath is drawn whole in the opening; with nothing under it the top is shown as photographed, and the closet always shows it whole. Outerwear worn open never shows the inside of its back. A yes/no question made the model call a zipped cardigan open, and it reads the neck of an opening well but the hem badly — so the answer is an enum and a bad hem is replaced by a narrow gap under the neck. Because the AI can still get it wrong, the item card has an **Open front / Closed front** row for tops and outerwear; marking a piece open by hand gives it a typical opening.
- The item card got a **Remove from wardrobe** row (red, like Log out) — learner request: it asks once more, then deletes the item and its picture and returns to the closet.
- Background removal got a **repair step** — the learner's cream striped beanie on a white backdrop came out half see-through and grey, and the damaged cutout was then tagged as a scarf. u2net was unsure about two thirds of that piece (a clean cutout is unsure only along its edge), and the tool darkens whatever it is unsure about. When the first model is unsure about 45% or more of the piece, a second model (isnet-general-use) is asked for its mask, the stronger answer wins per pixel, the mask is made solid, stray specks are dropped, and the colors are taken from the photo. Combining the two models on *every* photo was tried first and dropped: it left patches of backdrop around a scarf that u2net alone had cut out cleanly, and doubled the wait. Measured on 19 of the learner's photos: only the beanie crosses the limit (0.69; the next is a bag on a thin chain at 0.28).
- The wardrobe (database + item pictures) is not in git, and a full disk had just crashed Docker — so `scripts/backup.sh` and `scripts/restore.sh` were added. Backups go to iCloud Drive by default; they are run by hand, not on a schedule.
- Slice 6 was built before slice 5 and grew — learner request. Saving follows design page 17 ("Your fit for today" after Next), but instead of the chips with piece names the card has rows like the item card: the clothes in the outfit, its colors (taken from the clothes), its category (the same list as item tags: Casual, Work, Date night…), its seasons, and **Delete outfit** with a confirmation. The same card opens a saved outfit from the Outfits tab. The spec's `source` / `hint` columns were dropped: nothing shows them.
- **Wear it today** and a simple **Calendar** tab came into the PoC — learner decision; `scope.md` had the outfit calendar under Later and `prd.md` had it as "coming soon". Cost: one more table, two endpoints and one screen. Wear it today saves the outfit and puts it on today in one request; a day holds one outfit. Still out: streaks, the weather on empty days, OutfitCHECK photos, and the share button (it says "Coming soon").
- A saved outfit keeps a **picture** of the look, drawn by the canvas itself, instead of being rebuilt from its pieces wherever it is shown — the layering on the canvas (half a jacket, a collar under a sweater, accessory spots) lives in one screen, and the Outfits grid, the card and the calendar only need to show an image. The price: the picture doesn't change if a piece's photo is edited later.
- Removing a piece from the wardrobe takes it out of the saved outfits that had it, and the outfits stay with their picture as saved — the alternative (deleting those outfits, and with them their calendar days) would lose history because one T-shirt was thrown away. Deleting an outfit does remove its calendar days, and its dialog says so.
- Follow-ups from the learner's check of saved outfits: the calendar's blank cells show the neighboring months' dates on beige, and a calendar icon opens a month and year picker; the outfit cards in the Outfits tab are half see-through; Home got **search** (a magnifier in the header; by a piece's name or type) and **filters** behind the three lines — clothes by color, type, tags and season, outfits by the colors and kinds of piece of their clothes, category and season. Her rule for outfits: with several colors chosen the outfit must have all of them. Filtering runs on the phone, because both lists are already loaded in full; her "weather filter" was built as the outfit's season, the only weather-like label an outfit has.
- The AI stopped tagging new pieces (2026-10-16): the first model in the list answered photos with "503 high demand" after ~38 s, and with thinking on, the flash models needed 8-9 s for the tagging request — over the 8 s limit — so every model failed and the piece was saved without type and color. The tagging call now asks for no thinking (about 3 s; the stylist keeps it), each model gets 12 s within a 20 s total, and a model that just failed is tried last for ten minutes. Also on the learner's request: every piece on an outfit's card opens that piece's own card.
- Saved outfits can be changed — learner request: **Edit** puts the outfit back on the canvas, and after Next the user chooses **Save as new** or **Update**. On her follow-up, days on which an outfit was already worn never change: before a worn outfit is updated, its days move to a copy of it as it was (`replaced_by`), shown from the calendar as "As you wore it". Her rule for type changes: when a piece's new type has no room in a saved outfit (the outfit already has such a piece), an error says so and nothing changes; when the place is free, the piece moves there. The other problems found while thinking it through are handled too: saving the same outfit twice (refused, with a way to open the existing one), the outfit deleted while being changed (offer to save as new), a piece that can't be put back where it was (left out, with a note), a slot the outfit had lost (filled in from the closet, with a note), a piece changed on its card while the look is open (taken out of the look). Found while testing: a cap had been tagged "Top" by the AI under the old tagging settings; all models tag it as a cap now, and it was corrected.
- The Gemini model list now starts with the stronger flash models (gemini-3.6-flash, gemini-3.5-flash, then the lite ones) — learner decision. The lite models had gone first for their larger free quota; on 2026-10-16 the first of them was often overloaded and had tagged a cap as a top, and with tagging no longer thinking the flash models answer in 2-4 s. A few uploads a day fit their smaller quota; the lite models remain the fallback.
- The models are raced instead of tried one after the other: after the restart, tagging failed again, because at 16:00 the flash models needed 18-27 s while a lite model answered in 4 s, and trying them in turn (12 s each, 20 s in all) never reached it. Now the first model is asked; if it hasn't answered within 5 s (10 s for the stylist, which thinks) or has failed, the next one is asked as well, and the first valid answer wins; a model that failed or was outrun is tried last for ten minutes. On a slow hour an upload may cost two or three requests of the free quota instead of one.
- Slice 5 was built after slice 6. Every outfit needs a top, bottoms and shoes — learner rule while checking slice 5: the canvas may show a look with an empty slot (its dashed placeholder offers to add the piece), but Next asks for the missing piece and the backend refuses to save or update an outfit without all three (it had accepted any single piece). The "outfit with one piece" the learner saw was a test state: the trousers of a test account had been hidden on purpose to try the bottom placeholder.
- A dress replaces the bottoms — learner decision after the three-piece rule (it had been typed as a top that needed bottoms too). The learner's own design for it: the dress hangs over the place of the bottoms like a long coat, and the bottoms carousel starts on an empty page from which leggings or jeans can still be chosen. A dress and shoes are a complete outfit on the backend and on Next; the stylist adds bottoms to a dress only when the model chooses them. Checked on a test account with a stand-in dress (a coat photo typed Dress), since the learner's closet has no dress yet.
- A color and type filter on the canvas — learner request during the feature freeze, after its cost (2–3 hours, the canvas again) was explained; built with the Home filter sheet. Her rules: only color and type; a carousel the filter leaves empty says that no such pieces match (the learner's answer), and the filter can be removed. Decided while building: a type narrows only its own carousel, the filter isn't kept after the canvas closes, and it clears itself when the stylist's look or a newly added piece would be hidden by it (the stylist still chooses from the whole closet).
- Outerwear is as wide as the top it is worn over — learner feedback while checking slice 5 ("shoulder to shoulder, the size of the top"): a jacket had been fitted between the top's shoulder line and its hem, so a longer jacket came out narrower than the T-shirt under it.
