How it works, in plain language

The Android app is what you see and tap. It does no AI itself, holds no secrets, and only remembers who you are.

The Spring Boot backend is the brain. It cleans photos, asks the AI what each item is, saves everything, and answers the app.

PostgreSQL is the backend's spreadsheet (users, items, outfits). The photos themselves are files in a folder.

rembg cuts out backgrounds in its own container. Gemini tags items and acts as the stylist.

The key rule: the backend never trusts the AI blindly. Every item the stylist picks is checked against your wardrobe and the right category before it reaches the screen.

The core journey through the system

Open the app & sign up

implements prd.md › Account and Session
  1. SplashActivity checks SessionStore for a saved userId. If it finds one, it goes straight to the wardrobe.
  2. With no session: WelcomeActivity → AuthActivity (name + city).
  3. POST /api/users inserts a row in users and returns {id, name, city}. A taken name returns 409.
  4. The app saves the id, shows “Welcome to Mixyn, {name}!”, then opens MainActivity.

Add a piece of clothing

implements prd.md › Adding Clothes · AI Item Details
  1. Central + → AddMenuSheet → Photo Picker → AddItemActivity shows “Removing background…”.
  2. POST /api/users/{id}/items sends the photo as multipart.
  3. RembgClient → rembg container → transparent PNG.
  4. ImageStorage saves /data/images/{uuid}.png.
  5. TaggingService → Gemini (image + prompt) → {category, colorName, colorHex}.
  6. A row is saved in items and the item JSON is returned → “Background removed · 1/1 completed” → View item.
ui/additemitem/ItemServiceai/RembgClientai/TaggingServicestorage/ImageStorage

Item card & corrections

implements prd.md › AI Item Details
  1. ItemDetailActivity loads the image with Glide from GET /images/{file}.
  2. It shows Category, Color, Name, Tags, Season.
  3. Each change sends PATCH /api/items/{id}. This is how the user fixes the AI's guess.
  4. If tagging failed, the category is blank: “choose a category.” Uncategorized items stay off the canvas.
ui/itemitem/ItemController

Outfit canvas & swiping

implements prd.md › Outfit Canvas and Carousel
  1. OutfitCanvasActivity loads items once and groups them by category.
  2. It picks a random index per slot on the phone, with no server call.
  3. Each slot is a horizontal ViewPager2, so swiping one slot changes only that piece.
  4. Outerwear overlaps the top. An empty category shows a dashed placeholder with “Add shoes to complete the look.”
ui/canvas/OutfitCanvasActivitySlotPagerAdapterPlaceholderView

Generate with AI

implements prd.md › AI Stylist
  1. POST /api/users/{id}/outfits/generate {hint}
  2. StylistService builds a text list: id | category | color | name | tags.
  3. Gemini returns {topId, bottomId, shoesId, outerwearId, hintMatched}.
  4. Validate: each id must be yours and in the right category. Invalid slots get a random valid item; empty categories get null.
  5. If there's no match: “We couldn't find anything {hint}. Here is another stylish option!”
  6. The app scrolls each slot to the returned item and shows the toast if needed.
outfit/StylistServiceoutfit/OutfitControllerStylistServiceTest

Save the outfit

implements prd.md › Saving Outfits
  1. Save → POST /api/users/{id}/outfits {topId, bottomId, shoesId, outerwearId, source, hint}.
  2. Ownership is checked, and a row goes into outfits.
  3. OutfitsFragment lists them via GET /api/users/{id}/outfits, newest first.
  4. They're still there after reopening: Postgres lives in the pgdata volume.

Run it & record it

  1. cp .env.example .env, then add your Gemini key (never commit it)
  2. docker compose up --build starts Postgres :5432, rembg :7000, and the backend :8080
  3. curl localhost:8080/api/health should return {"status":"ok"}
  4. Open android/ in Android Studio → emulator → Run (the app calls 10.0.2.2:8080)
  5. Do one warm-up upload (rembg downloads its model on the first use), then record the demo

When things break

rembg fails or the photo is unreadable
Nothing is saved; the processing screen shows “We couldn't process this photo” + Try again.
Gemini tagging fails
The item is saved anyway with a blank category, and the card asks you to choose. The upload never fails because of tagging.
Gemini stylist fails or returns bad ids
Bad slots are filled with random valid items. On total failure: “The stylist is taking a break — here's a random look instead.” The canvas is never blank.
The emulator can't reach the backend
“Can't reach Mixyn — is the server running?” Check that you're using 10.0.2.2 and that the network security config is present.

Verify early in the build

  • The current Gemini Flash model id, the free-tier limits, and the Java SDK calls for image input + JSON schema
  • The rembg server command, endpoint, and field name (one curl test)
  • The latest Spring Boot 3.x version

Learning focus: treating AI output as untrusted input, meaning a schema, then validation against the database, then a fallback. The evidence will be StylistServiceTest plus a no-match hint still producing a full look.
